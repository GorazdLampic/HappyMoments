HappyMoments Implementation Plan

From current app to canonical UX spec · June 2026
Based on: ux-guidelines.html, onboarding-flow.html, navigation-architecture.html, user-psychology.html

Strategy: 4 Phases, Ship After Each

Principle: Each phase produces a deployable version. No "big bang" rewrite. Each phase makes the app better on its own, even if the later phases never happen. Test with real users after each phase.

Risk: This is the most structurally disruptive phase. The switchTab() function, all tab references in JS, and the CSS layout all need updating. Existing users who know the 4-tab layout will notice the change. Mitigate by keeping ALL functionality accessible — nothing is removed, just reorganized.

What to preserve

  • All functionality from Team tab → moves to Home as a section
  • All functionality from Settings tab → moves to Profile panel
  • All functionality from Data tab → becomes the People tab
  • Person columns view (existing daily users may prefer it) → keep as the People tab's per-person view

How to test

  1. Open app with existing data (2+ people) — Home should show hero + milestones + Together
  2. Tap People tab — should show people list, tap person → their milestones
  3. Tap profile icon — should open settings panel
  4. Check: can you reach every old feature in ≤3 taps?
  5. Check: tab bar stays fixed at bottom while scrolling

The big decision: person columns vs time list

Keep both, surface differently. Time-chunked list is the DEFAULT on Home (what's coming soonest?). Person columns become the per-person view inside the People tab (tap a person → see their milestones). This way daily users get the time-first view, but users who want to explore by person can do so in the People tab. No functionality lost.

How to test

  1. Open app with 3+ people — Home should show hero + chunked list + Together + Add someone
  2. Milestones should be grouped by proximity (This week, This month, Later)
  3. Together section should show one combined milestone
  4. Scroll to bottom — "Add someone to celebrate" always visible
  5. Empty state: open with 1 person, no milestones this week — should show motivational message

Implementation Order Within Each Phase

Within each phase:
  1. HTML first — structure the screens/elements
  2. CSS second — style them
  3. JS third — wire up the logic
  4. Test — ?reset for onboarding, normal for daily use
  5. Build + push — deploy to Cloudflare

What We Intentionally Do NOT Change

These stay as they are (from ux-guidelines.html §8. What We Protect):

  • The billion-second hook concept
  • Counter animation on reveals
  • Pre-written share messages (1000+ templates, 6 languages)
  • PWA capability
  • 21-language support
  • Local-first data (no account required)
  • Milestone calculation engine (specialNumbers.js, milestoneCalculator.js)
  • API backend (Cloudflare Functions, D1, Stripe)
  • Android build pipeline (GitHub Actions)

Risk Mitigation

RiskMitigation
Existing users confused by nav changeAll features remain accessible. Nothing removed, only reorganized. Consider a one-time "What's new" overlay on first open after update.
Onboarding regression?reset testing after each change. Track onboard_complete rate before and after.
Combined milestones lostTogether section on Home ensures visibility. Also accessible from People tab.
Phase 2 breaks somethingMost structurally risky phase. Do it in a git branch, test thoroughly before merging. Keep old tab code commented, not deleted.
Too many changes confuse beta testersShip Phase 1 first, get feedback, THEN Phase 2. Don't batch.
